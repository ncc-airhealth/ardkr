# capture-knowledge

새로 알게 된 지식 중 기억해야 할 것은 그 자리에서 기록한다.
나중에 몰아서 정리하지 않는다.

## knowledge/에 기록하는 것

knowledge/는 간접 지식을 다룬다.

- **의사결정** — 무엇을, 왜, 어떤 대안을 기각하고 정했는지
- **기관/담당부서 문의 결과** — 무엇을 물었고 어떤 답을 받았는지 (문의 방법·경로 포함)
- **데이터 처리 방법 / 재사용 예시 코드**
- **주의사항·경험칙** — "이 데이터는 매년 4월 갱신", "이 소스는 좌표계 확인 필요"
- **참고한 연구·외부 자료**

## STAC에 기록하는 것

특정 데이터셋의 **사실**(좌표계·컬럼 의미·결측값·정정 이력·기관 해명)은 STAC 메타데이터에 기록한다.
STAC `description`에는 무엇을, 왜, 어떤 근거로 고쳤는지 자연어로 적는다. 주체는 실명이 아니라 기관·부서 단위로 표기한다.

판단 기준: "이 데이터셋 하나에 대한 사실"이면 STAC, "여러 작업에 걸친 방법·판단·맥락"이면 knowledge/.

## 기록 절차

1. **위치를 고른다.**
   - 설계·운영 결정은 `knowledge/decisions/<파일명>.md`에 쓴다.
   - 그 외 개념(기관 연락·경험칙·처리법 등)은 `knowledge/<파일명>.md`나 하위 디렉토리에 쓴다.
     관련 개념이 묶이면 디렉토리를 만들고 `index.md`로 그룹화한다.
   - 기존 문서에 이어지는 내용이면 새 파일 대신 기존 문서를 갱신한다.

2. **OKF frontmatter를 단다.** (`type`은 필수)

   ```yaml
   ---
   type: decision | contact | heuristic | howto | reference | ...
   title: <한 줄 제목>
   description: <한 문장 요약>
   tags: [<검색용 키워드>]
   timestamp: <오늘 날짜 ISO 8601, 예: 2026-07-20>
   ---
   ```

   - `type`은 자유 문자열이다. 내용에 맞게 짧게 짓는다.
   - `timestamp`는 반드시 오늘 날짜로 기록한다 (갱신 시 갱신일로 수정).
   - `title`·`description`도 아래 문체 규약을 그대로 따른다. 본문을 고치면 description이 여전히 맞는 요약인지도 같이 확인한다 — 본문만 고치고 description은 옛 내용 그대로 두면 문서가 자기모순을 갖는다.

3. **본문은 구조화한다.** 자유 산문보다 제목·목록·표·코드블록을 선호한다.
   decision type 문서는 결정 / 근거 / 기각한 대안 / 미해결 구조를 따른다.
   외부 출처는 `# Citations`에 적는다.
   기각한 대안에는 결론과 근거만 적는다 — "몇 번째로 검토했는지", "실제 확인 후"·"검토 후" 같은 과정 서사는 뺀다.
   예: "lock 파일 별도 경로 안 — uv가 지원하지 않아 기각. 스크립트 옆에 유지."
   실질적 이유가 있는 과거 대안 비교(예: 이름을 한 번 바꾼 이력)는 기각한 대안 섹션에만 적는다. 본문 다른 곳에서 같은 이력을 반복 서술하지 않는다 — 한 사실은 한 곳에만 적는다.
   특정 loanword나 표현을 여러 문서에 걸쳐 고치기로 했다면, 그 표현 그대로 `grep -rn`을 한 번 돌려 놓친 문서가 없는지 확인한다. 매 캡처마다 하는 전체 감사가 아니라, 그렇게 용어를 바꾸기로 결정했을 때만 하는 targeted 확인이다.
   목록 항목 하나에 문장이 여러 개면 첫 문장만 그 항목 자체로 두고, 나머지 문장은 한 단계 들여쓴 하위 항목으로 각각 분리한다. 가독성이 목적이다.
   예:
   ```
   - 메타데이터는 JSON으로 직접 작성해 git의 `stac-metadata/`에 커밋한다.
     - 커밋된 JSON이 diff·PR 리뷰 대상이 되어 원칙 1·2와 정합한다.
     - 버전 차원은 `stac-metadata/`에 둔다.
   ```

4. **링크를 건다.** 관련 문서는 `/`로 시작하는 경로로 연결한다. 경로의 기준점은 knowledge/다.
   예: `[/decisions/reproducibility.md](/decisions/reproducibility.md)`.
   기존 문서의 헤딩 제목을 바꾸거나 지울 때는, 그 정확한 제목 문자열로 `grep -rn`을 한 번 돌려 다른 문서가 그 제목을 이름으로 인용하고 있는지 확인한다. 매번 전체를 훑는 게 아니라, 헤딩을 실제로 고칠 때만 하는 targeted 확인이다.

5. **`index.md`를 갱신한다.** 새 문서를 추가했으면 해당 디렉토리의 `index.md` 목록에 한 줄(제목 + 한 줄 설명) 추가한다.

6. **쓴 뒤 처음부터 다시 읽으며 검토한다.** 방금 쓴 사람이 아니라 처음 보는 사람 입장에서 다시 읽는다. 아래 문체 규약과 하나씩 대조해 어긋나는 문장을 고친다.
   자기 검토는 기계적 위반(정해둔 loanword, 격에 안 맞는 표현, 목록 구조 등)은 잡아도 애초에 규약에 없던 새로운 종류의 어색함까지는 못 잡는다.
   그래서 이 검토는 1차 방어선일 뿐이고, 최종 검증은 여전히 사용자 피드백 루프의 몫이다 — [/decisions/governance-and-review.md](/decisions/governance-and-review.md)가 이미 정한 self-review 원칙과 같은 이유다.

## 문체

문서는 사람이 읽는다. 기계적으로 압축하지 않고, 사람에게 설명하듯 쓴다.
번역투로 쓰지 않는다. 이 저장소의 독자는 한국어로 생각하는 사람이다.
결론과 근거만 남긴다. 쓰는 사람이 거친 과정은 지운다.
기호가 아니라 문장으로 말한다.
한 문장에는 생각 하나만 담는다.

검증 방법은 키워드 목록을 grep하는 게 아니라 처음부터 끝까지 소리 내어 읽어보는 것이다.
grep은 미리 떠올린 단어만 잡으므로, 예상 못한 어색함은 그 방식으로 절대 못 잡는다.
아래 예시는 체크리스트가 아니라 "이런 부류의 문제가 있다"는 참고일 뿐이다. 실제 판단은 매 문장을 읽으며 직접 한다.

- 논문 문장처럼 명확·간결하게 쓴다. 약어·추상 명사(SSOT 등) 대신 실제 내용을 직접 서술한다.
  예: "SSOT는 STAC이다" 대신 "데이터에 대한 메타데이터는 STAC에만 작성한다".
- 영어 표현을 그대로 옮긴 의인화·직역 서술을 쓰지 않는다.
  예: "버전 차원은 `stac-metadata/` 아래에 산다"("lives under"의 직역) 대신 "버전 차원은 `stac-metadata/` 아래에 둔다".
  예: "옛 버전이 얼어붙은 뒤에 발견되고"("frozen"의 직역, 한국어 화자에게 부자연스러움) 대신 "옛 버전이 이미 발행되어 더는 손댈 수 없게 된 뒤에 발견되고".
- 대응하는 한국어가 있는 영어 명사를 그대로 쓰지 않는다.
  예: caveat → 주의사항, convention/컨벤션 → 관행, gap → 빠진 부분, placeholder → 임시값, staging → 준비 단계.
  단 STAC/코드 스펙 자체의 고유 개념어(asset, extent, checksum, provenance 등)나 실제 도구·경로 이름(pipeline, STAC, Docker)은 예외다 — 이건 번역하면 오히려 무엇을 가리키는지 불분명해진다.
- 격에 안 맞는 구어체 동사를 쓰지 않는다.
  예: "박다"·"못박다"(비유적 구어 표현) 대신 "명시한다"·"고정한다"·"규정한다".
- 본문은 현재 상태를 남긴다. 발행 전 초안 단계에서 있었던 사소한 뒤집기는 최종 상태만 남기고 지운다.
  예: "최초엔 `linux/amd64`로 시작했다가 같은 날 뒤집었다. 발행 전 draft라 정정이 아니라 그냥 고쳐 쓴 것이다" 같은 문장은 지우고, 최종 상태("단일 정규 arch로 `linux/arm64`를 쓴다")만 남긴다.
  이런 뒤집기의 흔적은 지금 설계를 이해하는 데 아무 의미가 없다.
  반대로 실질적 이유(정책 충돌 등)로 접근을 바꾼 기록이나, 재발 방지가 필요한 운영상 경고("uv가 `git+` 의존성을 풀려면 `git`이 필요하다")는 남긴다 — 지금 상태를 이해하거나 같은 실수를 반복하지 않는 데 쓰이기 때문이다.
  "~하지 않는다" 같은 부정문도 같은 기준으로 가른다. 과거와 비교하려고 쓴 부정문("검토했으나 채택하지 않았다")은 지우되, 그 자체가 지금의 실제 규칙인 부정문("CI는 도입하지 않는다", "삭제는 금지한다")은 그대로 둔다.
- 마크다운 소스에서 한 문장은 항상 한 줄로 쓴다. 줄바꿈으로 문장을 잘라 다음 줄에 잇지 않는다.
- 괄호 안에 괄호를 쓰지 않는다. 부연 설명이 필요하면 별도 문장으로 뺀다.
- "실제로"·"사실상"·"기본적으로"처럼 빼도 뜻이 안 바뀌는 부사는 쓰지 않는다.

## 규약

- **개인정보 최소화**: 실명·이메일·전화보다 기관·부서 단위 귀속을 기본으로 한다("OO부 OO과에 문의" 형태).
- **경험칙은 중립·증거 기반**으로: "이 기관은 조작한다"(비난) 대신 "2019/2020 좌표계 불일치 확인됨"(증거).
- **포착은 진위를 보장하지 않는다.** 적힌 게 참인지는 사용자 피드백 루프가 사후에 검증한다.
  그러니 인용한 자료나 문의한 경로를 함께 남긴다.
